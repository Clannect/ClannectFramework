Signals

A signal tells whoever is listening that something happened. It is plain C++: no code generator and no macros.

Declare, connect, emit

A signal is a public member, with the types of what it sends. The functions connected to it are called slots.

#include "cfw/core/Signal.h"

class World {
public:
    cfw::Signal<Instance &> instanceAdded;
};

// Listen:
cfw::ScopedConnection connection = world.instanceAdded.connect([](Instance &instance) {
    // ...
});

// Tell every listener:
world.instanceAdded.emit(part);

Widgets work the same way. A button's clicked is a signal, and so is a window's pointer.

Ending a connection

connect returns a Connection. What you do with it decides how long the slot stays connected:

Keep it asThe slot is disconnected
ConnectionOnly when you call disconnect(). Destroying a Connection does not disconnect.
ScopedConnectionWhen the ScopedConnection is destroyed. It can be moved but not copied.
Nothing: pass a SignalOwner to connectWhen the owner is destroyed.
Do not let a slot outlive what it uses

A slot that captures this or a local variable by reference must be disconnected before that object is gone. Use a ScopedConnection or a SignalOwner, not a plain Connection.

SignalOwner

An object that listens to several signals can derive from SignalOwner, or hold one as a member. Every connection made through it ends when the object is destroyed:

#include "cfw/core/SignalOwner.h"

class Explorer : public cfw::SignalOwner {
public:
    explicit Explorer(World &world) {
        world.instanceAdded.connect(*this, [this](Instance &instance) { addRow(instance); });
    }
};

As a base class, SignalOwner disconnects after the derived destructor has run. If a slot could be called while the derived part is being torn down, call disconnectAll() first thing in the derived destructor.

The rules of an emission

All of this is defined behaviour, and tested:

  • Slots run at once, on the calling thread, in the order they were connected.
  • A slot connected during an emission is not called by that emission.
  • A slot disconnected during an emission is not called for the rest of it. A slot may disconnect itself.
  • A slot may emit the same signal again.
  • A slot may destroy the signal, or the object that owns it. The emission stops after that slot returns, and nothing is left dangling.
  • Every slot sees the same arguments, so a signal cannot carry an rvalue reference.

Threads

A signal belongs to one thread, its owner's, and is not synchronised. It does not deliver across threads: to reach another thread, post to that thread's event loop and emit there.

Cost

Connecting allocates. Emitting does not.

Why it works this way

Signals, connections and running emissions can each be destroyed first, in any order. The record of that decision is 0004: signal and slot lifetime.
