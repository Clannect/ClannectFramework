Security checks

A workflow called cfw-security-guard scans the whole repository on every push and pull request, every day, and before every release.

Why it exists

CFW is built into other people's software. Harmful code that got into CFW would reach everyone who uses it. The guard is there so that a risky change cannot arrive unnoticed.

What it checks

JobWhat it looks forWith
malwareKnown malware in any file.ClamAV, with signatures updated in the run.
sastRisky C and C++: starting other programs, injecting code, loading libraries at run time, unsafe copies and format strings.Flawfinder (levels 4 and 5) and CFW's own scan.
supply-chainCMake, Python and shell that download or run things; committed executables.CFW's own scan and Bandit.
verdictWhether every job above passed.

The verdict job writes the result at the top of the run's summary: :) CLEAN or :( CRITICAL FAILURE.

It fails closed

A job fails when it finds something. It also fails when it could not do its work: when the malware signatures could not be updated, when a scanner could not read a file, or when it scanned fewer files than there are. A job that did not run counts as a failure too.

The allowlist

Some CFW code does risky-looking things on purpose. cfw-io starts other programs, because that is what its Process class is for. cfw-audio loads the system's sound library at run time.

These accepted cases are listed in .github/security/allowlist.txt, one line each: a rule, a file, and how many times it may occur. Anything that is not on the list, or occurs more often than the list says, fails the run.

Changes near the allowlist take longer to review

A pull request that edits a file named in the allowlist, the allowlist itself, or anything under .github/ is inspected by hand by the Clannect team, even when the verdict is clean. See CONTRIBUTE.md.

If your pull request fails

  1. Open the failed run and read its summary. It names the rule, the file and the line.
  2. For more, download the logs from the run's artifacts: security-logs-malware, security-logs-sast and security-logs-supply-chain.
  3. If the finding is a mistake in your change, fix the code.
  4. If the call is really needed, add or raise its line in the allowlist in the same pull request, and say why in the description.

You can run two of the scans yourself, from the repository's root:

python3 .github/security/cfw_guard.py cxx
python3 .github/security/cfw_guard.py supply-chain

What it cannot do

The source scans read the code as text. They catch a risky call that is written down, not one that is put together while the program runs. The guard is an alarm that makes a person look. It is not proof that the code is safe.
